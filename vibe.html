Библия
вайбкодинга как писать софт быстро и не сойти с ума

Написано человеком, который не умеет программировать — за два часа практики с машиной.

Вайбкодинг — это когда ты делаешь программы короткими итерациями: сделал → проверил → улучшил. Не полгода плана, а неделя рабочего прототипа. Но без правил скорость превращается в хаос: сегодня фича за час, завтра полдня ищешь, почему всё сломалось.

I · главный принцип

Скорость — это быстрый откат.

Скорость это не «писать быстро». Это «быстро откатываться и быстро проверять». Всё остальное — следствия.
не скорость
  • добавил кнопку
  • старая форма сломалась
  • не помнишь, что именно менял
  • откатить не можешь
настоящая скорость
  • понимаешь, что сломалось
  • за минуту возвращаешь рабочую версию
  • пробуешь по-другому
«Быстро» без возможности откатить — это «быстро копить проблемы».
II · тринадцать правил

Правила выживания.

Сохраняют скорость и не дают проекту развалиться.
01core

Маленькие шаги.

Каждое изменение должно быть маленьким, обратимым и проверяемым. Меняешь одну вещь за раз. Можешь вернуть как было. Сразу видно — работает или нет.

плохо
«Переделал дизайн + добавил регистрацию + поменял базу». Что-то сломалось — где именно? Хрен знает.
хорошо
«Добавил кнопку зарегистрироваться.» Проверил — работает. Сохранил. Следующий шаг.

Если шаг кажется слишком большим — раздели на два-пять шагов поменьше.

02tooling

Всегда можно вернуться назад.

У тебя всегда должен быть способ вернуться к рабочей версии за 30 секунд.

  • Используй Git.
  • Делай короткие коммиты.
  • Пиши понятные сообщения: добавил кнопку логина.

Без отката каждое изменение — риск. С откатом ты можешь экспериментировать смело: не работает — вернул за секунды.

03structure

Не смешивай слои.

В любой программе есть три слоя:

логика
«пользователь может купить только если есть деньги»
интерфейс
«кнопка „купить“ зелёная или серая»
данные
«цена товара», «список категорий»

Если логика размазана по интерфейсу, изменение правила требует перелопатить все кнопки. Если она в одном месте — правишь в одной точке.

04structure

Один источник правды.

Если одна и та же информация хранится в двух местах — рано или поздно они разойдутся.

  • Расчёт скидки и на сервере, и в приложении.
  • Список ролей и в коде, и в базе.
  • Проверка email и в форме, и в API.

Выбери одно место как источник правды. Всё остальное берётся оттуда.

05structure

Ставь границы.

Чтобы изменения не расползались по всему проекту, создавай точки соприкосновения — контракты.

Между фронтендом и бэкендом есть API (договор). Если договор чёткий:

  • фронтенд можно переделать — бэкенд не сломается
  • бэкенд можно улучшить — фронтенд не сломается
06workflow

Чини, не переписывай.

соблазн
«Мне не нравится этот файл, перепишу его полностью.»
практика
Меняй минимальный участок, который решает задачу.

Полная переписка теряет мелкие исправления, возвращает старые баги и затрудняет понимание того, что изменилось.

07workflow

Три режима — не смешивай.

feature
«делаю новую кнопку „поделиться“»
fix
«исправляю: форма не шлётся на iphone»
refactor
«переношу валидацию в отдельный файл»

Один коммит — один режим. Смешаешь feature с рефакторингом — что-то сломается, и будет непонятно где.

08tooling

Проверяй каждый шаг.

У тебя должна быть одна команда, которая проверяет: живо ли приложение?

  • запускается?
  • основной сценарий работает?
  • нет критических ошибок?

Вайбкодинг без проверок = лотерея. Ты не знаешь, сломал ли что-то, пока пользователь не напишет «у меня не работает».

09tooling

Логи — твои глаза.

Чем быстрее меняешь код, тем важнее видеть, что происходит.

[INFO]    user 123 logged in
[ERROR]   email send failed: connection timeout
[WARNING] slow query: 5s

Без логов ты слепой. С логами — быстро находишь проблему и видишь паттерны.

10tooling

Конфиги и фичефлаги.

Фичефлаг — это выключатель для экспериментов.

if (featureFlag.newCheckout) {
  // new path
} else {
  // old path
}
  • можно включить для 10% пользователей
  • сломалось — выключил без деплоя
  • сравнил метрики: что лучше?

Вайбкодинг = «давай попробуем». Флаги делают пробы дешёвыми.

11structure

Выноси данные наружу.

Что часто меняется — не должно быть в коде.

плохо
if (product === "кофе") price = 200;
if (product === "чай")  price = 150;
// ... 100 строк
меняешь цену — лезешь в код, можешь что-то сломать.
хорошо
// prices.json
{
  "кофе": 200,
  "чай":  150
}
меняешь цену — правишь json, логика не трогается.

Выноси: цены, тарифы, лимиты, тексты интерфейса, списки категорий, правила бизнес-логики.

12team

Документируй только полезное.

Не пиши документацию ради документации. Пиши только то, что экономит время.

  • README.md — как запустить (3–5 команд)
  • ARCHITECTURE.md — как устроено (1 страница)
  • CHANGELOG.md — по одной строке на итерацию

Не пиши: очевидные вещи, устаревшую информацию, комментарии к каждой строке.

13workflow

Не держи всё в голове.

Мозг переполняется. Фиксируй решения.

  • TODO-листы для задач
  • Заметки о решениях: «почему выбрали postgres?»
  • Дневник разработки (опционально)

Через неделю забудешь, почему сделал именно так. Другим людям проще влиться. Себе же поможешь.

III · цикл

Идеальный цикл.

Одна итерация — 20–40 минут. В конце — рабочая версия. Десять циклов в день = десять улучшений, откатываемых за секунды.
01 · intent

Цель одной фразой.

«добавить кнопку смены пароля»

02 · boundary

Границы — что не трогаем.

«не меняю базу, не трогаю дизайн»

03 · patch

Минимальный патч.

1–2 файла, 10–50 строк

04 · check

Проверка.

запустил → нажал → работает

05 · commit

Фиксация.

git commit -m "…"

IV · что убивает вайб

Антипаттерны.

Шесть способов всё сломать. Все проверены лично.
× 01

«Щас быстро перепишу всё.»

Спойлер: не быстро. Потеряешь неделю.

× 02

«Потом починю.»

Потом — никогда. Технический долг растёт.

× 03

«Нет тестов, но работает.»

Работает, пока не тронул. Потом — сюрпризы.

× 04

«Смешаю refactor и фичу.»

Что-то сломается. Не поймёшь где.

× 05

«Дублирую логику в двух местах.»

Поменяешь в одном, забудешь в другом. Баг.

× 06

«Слишком умная архитектура до MVP.»

Три месяца делал «правильно». Оказалось, что фича не нужна.

V · контекст

Команда и переписывание.

если не один

Маленькие pull request'ы.

Не 3000 строк за раз. Лучше 10 PR по 200 строк.

Описывай «что» и «почему»:

# что
добавил фильтр по категориям

# почему
пользователи не могли найти товары

Автопроверки: линтер, тесты, сборка — всё автоматом.

Договорённости: имена веток, стиль коммитов, один форматтер.

вайб команды = предсказуемость + скорость

когда можно переписать

Редко. И с планом.

Переписывание имеет смысл только если:

  • ты чётко знаешь целевую архитектуру
  • есть тесты для проверки
  • старая система реально мешает
  • есть план миграции

Иначе переписывание — способ отложить проблемы и создать новые.

Лучше постепенно улучшать старое, чем за раз сделать «идеальное» новое.
VI · вайбкодинг с машиной

Пять наблюдений.

Я не программист. Я экспериментировал с машиной два часа. Вот что понял.
01

Машина делает вайбкодинг доступным.

Раньше нужно было знать синтаксис, фреймворки, паттерны. Теперь:

  • описал словами, что хочешь
  • машина написала код
  • проверил — работает или нет
  • уточнил, улучшил
02

Паттерны видны сразу.

Когда машина генерит код, проблемы становятся явными:

  • задублировала логику → нужен один источник правды
  • перезаписала весь файл → лучше бы патчем
  • смешала фичу и рефакторинг → вот почему сломалось
03

Скорость проверки — ключ.

Машина сгенерила пять вариантов. Проверил каждый:

  • 1 — не работает
  • 2 — работает, но криво
  • 3 — отлично

Без быстрой проверки я бы не понял, какой вариант рабочий.

04

Откат спасает.

Машина иногда генерит хрень. Но у меня git:

git checkout -- file.js

Без отката я бы боялся экспериментировать.

05

Маленькие шаги работают лучше.

плохо
«сделай мне весь проект сразу» → машина сгенерила 10 файлов, половина не работает, не понятно что чинить.
хорошо
«добавь кнопку. теперь сделай, чтоб отправляла данные. теперь добавь валидацию.» → каждый шаг рабочий, если что-то не так — понятно где.
VII · вывод

Не «кодить быстро».
Быстро экспериментировать безопасно.

Правила не делают код медленнее. Они делают его предсказуемым: быстро добавить фичу, быстро откатить, быстро понять — что сломалось.

С этими правилами вайбкодинг — это суперсила.
если дочитал — попробуй.
худшее, что может случиться — откатишь изменения за 30 секунд.
